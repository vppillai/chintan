# Alarms

Every stack with `enable_alarms: true` (`config/instances/*.yaml`) declares fifteen CloudWatch alarms in `infrastructure/template.yaml`, or fourteen when `daily_spend_cap_micros` is `0`, since an alarm on a cap that cannot trip would read green for nothing (`SpendCapAlarmEnabled`). Each is named `chintan-<instance>-<environment>-<suffix>`, publishes to the stack's `AlarmTopic`, and e-mails one address: the config's `alarm_email` when set, otherwise the `ALARM_EMAIL` repository secret, which `deploy-backend.yaml` passes to the production job only and `scripts/ci-deploy-stack.sh` drops with a warning when the config already has a value. Fourteen alarms are a sum over one period with one evaluation period and the dead-letter alarm a maximum; every one treats missing data as not breaching (a counter that was never emitted is the healthy state), and sends nothing on the return to OK; an alarm already in ALARM sends no second e-mail, so a repeat inside the window is silent. Beyond the account's ten free alarms CloudWatch bills $0.10 an alarm-month, which is why `dev-staging.yaml` sets `enable_alarms: false`: its deploy's smoke test is its alarm.

Ten of the `Chintan`-namespace metrics below are emitted with a rollup (`obs.CountWithRollup`, and `obs.EmitWithRollup` for `ExpiredNotesFailed`; `backend/internal/obs`), which publishes a dimensionless copy for the alarm beside the dimensioned one for the console; `TestEveryAlarmedMetricIsRolledUp` (`backend/internal/obs/rollup_test.go`) holds every alarm without `Dimensions` to that. `capture-reaped` is the one alarm with `Dimensions`: it reads `CaptureReaped{Outcome=failed}` directly, so the metric is emitted with plain `obs.Count`. The other four read AWS metrics. `metrics.md` lists every metric that is not alarmed and who reads it.

Logs: the API is `/aws/lambda/chintan-api-<instance>-<environment>`, the worker `/aws/lambda/chintan-worker-<instance>-<environment>`, the gateway `/aws/apigateway/chintan-<instance>-<environment>`; `metrics.md` has the `aws logs` recipe.

| Alarm (suffix) | Metric | Threshold, period | What it means | What to do | How it clears |
|---|---|---|---|---|---|
| `api-errors` | `AWS/Lambda` `Errors` on the API function | 5 or more in 5 min | The API function itself faulted: a panic, a timeout, an init failure. Not an application 5xx, which the next row counts. One fault is the client's retry's problem; five in a window is an outage. | Read the API log for the stack trace. If it began with a deploy, roll back (README → Operate → Rollback). | On its own, the first 5-min period with fewer than five faults. |
| `api-4xx` | `AWS/ApiGateway` `4xx` on the HTTP API | 300 or more in 5 min | One inbox route held at its throttle (`1` rps, burst `10`, in `ApiStage`'s `RouteSettings`) for the whole window admits 310 requests, and the gateway's own 429s count too: a public inbox route is being flooded with bad keys, or a client is stuck in a retry loop. Each refused request is billed before any key is checked. A stale token or one mistyped key cannot reach 300. | The gateway log carries `routeKey` and `status` per request (no source address: `AccessLogSettings` in the template). A revoked key still in use: **You → Devices & shortcuts**, remove the device. A probe: nothing to fix; the throttle bounds the cost. | On its own, the next quiet 5-min period. |
| `api-5xx` | `AWS/ApiGateway` `5xx` on the HTTP API | 5 or more in 5 min | Handlers are answering 500 on purpose: DynamoDB or S3 failing, or a bug the error mapper caught. The function did not fault, so `api-errors` is silent. | The API request log carries `route`, `status` and `duration_ms` per request (`obs/middleware.go`), and the error line beside it the cause; no user content. Check the AWS Health dashboard for the region before suspecting the code. | On its own, the next quiet 5-min period. |
| `inbox-key-refused` | `Chintan` `InboxKeyRefused` (`handler/inbox.go`, `deviceAuthenticated`) | more than 24 in 15 min | A device is still posting with a key that was revoked, has expired or was mistyped, or someone is walking key ids. Far above one wrong header, far below the flood above. | The console's `{Reason}` copy says `malformed`, `unknown`, `revoked`, `wrong_secret`, `expired` or `daily_limit` (`service/devices.go`). **You → Devices & shortcuts** shows which keys are live; paste the right key into the device or remove it. | On its own, the next 15-min period under 25. |
| `capture-dlq` | `AWS/SQS` `ApproximateNumberOfMessagesVisible` on `chintan-captures-dlq-<instance>-<environment>` | more than 0, 5-min maximum | One asynchronous worker invocation failed all three attempts and Lambda wrote its record here: a capture, or a scheduled or queued task (`sweep-expired`, `aws-cost`, `storage-snapshot`, `clean-note`, `ask`). The record names which. | Read: `Q=$(aws sqs get-queue-url --queue-name chintan-captures-dlq-dev-prod --query QueueUrl --output text); aws sqs receive-message --queue-url "$Q" --max-number-of-messages 10 --visibility-timeout 0`. A capture: the app's Retry. A scheduled task: it runs again on its schedule. A clean or an Ask: the next request. Then `aws sqs purge-queue --queue-url "$Q"`. | Only when the queue is empty. The message sits for 14 days (`MessageRetentionPeriod`), the alarm stays in ALARM, and a second dead letter in that time sends no e-mail — purge once acted on. |
| `provider-key-rejected` | `Chintan` `ProviderKeyRejected` (`pipeline/status.go`, `clean_note.go`, `ask.go`) | more than 0 in 5 min | Groq or the LLM endpoint answered 401 or 403. The key is revoked, expired or wrong, and every capture fails the same way until it is replaced; the person sees a fixed "key rejected" sentence, not "capture failed". | Put the new key in SSM (`/chintan/<instance>/groq_api_key` or `llm_api_key`, `SecureString`). The worker reads it at cold start (`resolveSecret` in `cmd/worker/main.go`), so redeploy or wait for the function to go cold; then Retry each failed capture in the app. The `{Provider}` copy says which key. | On its own, the first 5-min period without a rejection; nothing says OK, so confirm with a capture. |
| `capture-failures` | `Chintan` `CaptureStageFailures` (`pipeline/status.go`, `pipeline.go`, `append.go`) | more than 0 in 15 min | A capture failed in a stage: a provider 5xx, a reset connection, an undecodable answer, an append claim refused twice with nobody holding it, or a run that left the capture pending (`capture-orphaned` beside it). A provider fault ends the capture `failed` with a Retry button and returns cleanly to Lambda, so no retry and no dead letter say it happened; the threshold is one because nothing else does, and the counter has not fired in a month of several hundred captures, so one is signal. | The worker log names the stage (`stage`) and the cause (`error`). A provider: check its status page, then Retry in the app. A claim or a pending run: the capture was retried by Lambda; if it reached `capture-dlq`, that row. | On its own, the next quiet 15-min period. |
| `capture-orphaned` | `Chintan` `CaptureOrphaned` (`pipeline/pipeline.go`, `runCapture`) | more than 0 in 15 min | A worker run returned `nil` with the capture still in a stage — a stage that neither finished, failed nor conceded. `nil` is "done" to Lambda, so without the guard nothing would retry it and the row would sit where it stopped. The guard fails the invocation instead, so Lambda retries it, and counts it here by `{Status}`. | The worker log line `capture pipeline could not complete` names `capture_id` and `status`. The retry usually finishes it; if not, the reconcile task resumes or fails it within half an hour (`capture-reaped`). One is a bug: open an issue with the log line. | On its own, the next quiet 15-min period. |
| `capture-reaped` | `Chintan` `CaptureReaped{Outcome=failed}` (`reconcile/reconcile.go`) | more than 0 in 15 min | The quarter-hourly `reconcile-stuck` task found a capture pending past the stuck rule (`service.CaptureStuckAfter`, or the append lease), ran the pipeline once more, and it still did not finish, so the capture is now `failed` with the fixed sentence `Filing did not finish. Retry to try again.` `{Outcome=finished}` is the second run ending the capture on the pipeline's own terms and is not alarmed. The second run's own failure, if it was one, counted under `capture-failures` too, so one stuck capture can send that mail as well as this one; this one says the task gave up. An `uploaded` row whose recording has not landed is left alone, as the server's own Retry leaves it. | The worker log names the capture, the stage it was in and the second run's error. Retry in the app runs it once more; if that fails too the cause is in the log beside it. | On its own, the next 15-min period without one. |
| `push-send-failures` | `Chintan` `PushSendFailures` (`pipeline/notify.go`) | more than 2 in 15 min | The push service answered 5xx or was unreachable, once per subscription per send. A 404 or 410 prunes the subscription and is not counted. With one or two subscriptions, three in a window is every notification failing. | The worker log carries the status and the reason. Nothing on this side usually; if it persists, `scripts/vapid-keys.sh --instance <name>` (dry run) confirms the pair is in SSM, and **You → Notifications** off and on re-subscribes. | On its own, the next 15-min period under three. |
| `expired-notes-failed` | `Chintan` `ExpiredNotesFailed` (`purge/purge.go`, the sweep's `Failed` count) | more than 0 in 1 h | The weekly sweep (`rate(7 days)`) could not delete at least one archived note past its thirty-day deadline: its audio and text are still there. Emitted with `obs.EmitWithRollup` beside `ExpiredNotesPurged`. The sweep also returns an error, so its invocation retries and the third attempt reaches `capture-dlq`. | The worker log names the note ids and the error (a denied delete, a missing object). The sweep retries on its next run; `retention.md` has the rules. | On its own, within the hour (the metric is emitted only when the sweep runs). The notes stay until a sweep succeeds, so the alarm clearing is not the fault clearing. |
| `worker-messages-discarded` | `Chintan` `WorkerMessagesDiscarded` (`pipeline/worker.go`, `regenerate.go`) | more than 0 in 5 min | The worker dropped a message it could not parse: the API and the worker disagree on a shape, usually a deploy half-way between the two functions, or an event sent by hand. Dropped without retry, so the request never happens. | The worker log carries the reason. Let the deploy finish, then make the request again: Retry for a capture, Clean or Regenerate again for a note. One outside a deploy is a bug: open an issue with the log line. | On its own, the next quiet 5-min period. |
| `note-clean-invoke-failures` | `Chintan` `NoteCleanInvokeFailures` (`service/note_clean.go`, `pipeline/clean_note.go`) | more than 1 in 15 min | The API could not record a clean request or could not invoke the worker for it, so the note keeps a stale cleaned view and its "cleaning" promise. Two in a window is the API unable to reach the table or the worker. | The API log names the note and the error. The next save, or Clean pressed again, re-requests it. | On its own, the next 15-min period under two. |
| `provider-timed-out` | `Chintan` `ProviderTimedOut` (`pipeline/status.go`, `clean_note.go`) | more than 4 in 15 min | A stage's own deadline fired (`pipeline-deadlines.md`): the provider is answering, slowly. A stalled capture counts once per Lambda attempt, at most three, then lands in `capture-dlq`; five in a window is more than one recording waiting. | The worker log names the stage. Nothing to do on this side while the provider is slow; the captures retry on their own, and those that exhaust their attempts are in the dead-letter queue (that row). | On its own, the next 15-min period under five. |
| `spend-cap-tripped` | `Chintan` `SpendCapRejections` (`breaker/breaker.go`) | more than 0 in 5 min | The instance's daily provider spend reached `daily_spend_cap_micros`; every paid call is refused and each capture ends `spend_capped`. Refused on cost, not on failure — without this alarm the two look the same. Only declared when the cap is non-zero. | Expected on a heavy day: wait for the UTC day to roll over and Retry the captures (a `spend_capped` capture is retried at once). Unexpected: `CaptureSpendCapped{Stage}` says where it bit and `chintanctl usage` who spent it; raise the cap in the config only once that is understood. | On its own, the next 5-min period without a rejection; the cap itself resets at 00:00 UTC (`SPEND#<day>`). |

What has no alarm, on purpose: Lambda throttles (the reserved concurrency is out of a browser's reach), worker `Errors` (the dead-letter alarm says the same thing a minute later), a 5xx *rate* (an average over a quiet five minutes trips on one 500), and provider 429s (`ProviderRateLimited` is emitted and unalarmed; ordinary throttling clears on its own). The reasons are the comments above each alarm in `infrastructure/template.yaml`.
