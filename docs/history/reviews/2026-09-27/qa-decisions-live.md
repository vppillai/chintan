## Notes and observations (not failures)

1. **`GET /v1/push/key` 404 logs a console error on every You visit.** By design (`docs/design/push.md`: the card reads the 404 as "not set up here yet"), but Chromium prints "Failed to load resource: 404" for it each time You loads, so the You page can never have a clean console on an instance without VAPID keys. If that matters, the cheapest change is on the wire — e.g. `200 {"public_key": null}` or the card probing `HEAD` — rather than in the card. Files: `backend/internal/handler/push.go` (`getPushKey`), `frontend/src/features/settings/NotificationsCard.tsx`, `docs/api/openapi.yaml`. Optional.
2. **Deploy-window skew observed at 18:37.** The first A1 run saw the same 404 with the router's generic `"detail":"no route matches this path"`: the #133 frontend (with the card) was live before the #133 backend finished deploying. By 18:41 the sentence was the contract's. Transient and consistent with frontend-then-backend deploy order; the card treated both 404s the same. Nothing to fix; worth knowing when reading logs from a deploy window.
3. **GitHub Pages deep-link 404 document.** Opening `/settings`, `/about` or a note URL directly fetches the 404 fallback page first (`http 404 (non-API): GET …/chintan/dev/settings`), which is the SPA fallback for a static host and pre-existing; the app then renders normally. Counted as a resource 404, not an error.
4. **B2 script slip, not a product issue.** After the drag the fifth open row is "Sub-item 5" (Four at depth 1), so the script's wait for `Item 5` timed out (`qad-B2-mobile-ink-05-error.png` is just the settled list). Re-run as `qad-B2b.js`, which passed.
5. The `/v1/inbox/text` 202 capture was filed into "QA D inbox" as `transcribed` (a device text goes straight to cleanup). Both QA D notes were purged before this report was written.
