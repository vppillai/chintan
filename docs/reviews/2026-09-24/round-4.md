### Medium

**R4-1 A pin or unpin PATCH rewrites `updated_at`, so an unpinned note re-files under Today and a pinned note reads as edited** — backend, S, DO-NOW. (backend-data; confirmed and reproduced independently.) `PATCH /v1/notes/{id} {pinned}` goes through `UpdateNote`, where the `Pinned` switch added by #87 (`backend/internal/service/notes.go:488-506`) is followed by the pre-existing unconditional `note.UpdatedAt = model.Now()` (`:509`, blame 2026-08-07) and the unconditional meta `Put` (`:565`). `ReorderPins` in the same PR writes `PinRank` through `putCarryingStamp` without touching `UpdatedAt`, so within one feature a drag is not a touch but a toggle is. Live on prod: create → `updated_at …02:38:40 version=2`; `PATCH {pinned:true}` → `02:38:42 version=3`; a second `{pinned:true}` on the already-pinned note → `02:38:45 version=4` (so `docs/design/pins.md`'s "Pinning a pinned note changes nothing" is false today); `{pinned:false}` → `02:38:47 version=5`. The unpinned tier is ordered by `updated_at` (`repository/dynamo.go:783-789 NoteOrderKey`), Home groups by it (`frontend/src/features/notes/groups.ts`), every row shows it (`NoteRow.tsx:138,161`), and `usePinNote`'s optimistic patch keeps the old value then invalidates, so after the refetch an unpinned March note jumps to the top of Today and a pinned row's time becomes "now". Pins are the metadata toggle a person flips most, and the owner has already complained once about Home ordering. Fix: in `UpdateNote` compute `touched` as "any field other than `Pinned`/`ExpectedVersion` is set", and only then bump `UpdatedAt` and rewrite the meta object; keep the version bump through `putCarryingStamp`. Add a case to `handler/pins_test.go` (`TestPinnedNotesLeadTheListAndPageAcrossTheTier` or a sibling) asserting `updated_at` is unchanged across pin, pin-again and unpin.

(frontend-logic; confirmed by code and a live reproduction.) `NotesScreen.tsx:164` fetches `useNotes({state, tag, kind})`, `:302` splits pins out of that filtered list, `:713-718` renders `<PinnedGroup notes={pinned}>` with no filter awareness; the server applies the tag/kind `Keep` filter to the pinned tier too (`handler/notes.go:96-113`), so the group under a filter is a strict subset. `PinnedGroup.tsx:89` takes `ids = notes.map(id)` from that subset; both the drag (`:150`) and the grip arrow keys (`:219-228`) post it; `queries.ts:318-322` ranks the named ids from 0; `service/notes.go:606-644 ReorderPins` checks each id is pinned and active but never that the set is complete, and writes `rank = i × 1000`. **R4-3 Pin then Unpin before the list refetch lands sends the stale version, is answered 409, and leaves the note pinned with no message** — frontend-home, S, DO-NOW for the frontend half; backend half is Decision 6, OWNER. (frontend-logic; confirmed live at natural tap speed with no throttling; the verifier corrected two details, below.) `usePinNote` (`queries.ts:278-279`) sends the row's cached `version`; the optimistic patch (`:290-292`) writes `pinned`/`pin_rank` but not the version; there is no `onSuccess`, `onSettled` (`:303-306`) only invalidates, and `updateNote` returns the fresh `NoteWire` (`endpoints.ts:132-136`) that is thrown away. `busy` excludes `pin.isPending` in `NoteRow.tsx:134` and `NoteActions.tsx:97`. Live API: `PATCH {version:2, pinned:true}` → 200 v3; `PATCH {version:2, pinned:false}` → 409 `current_version:3`; note stays pinned. Live browser (Pixel profile, prod, no route delay): ⋮ → Pin, ⋮ reopened 127 ms later → Unpin → 409; after 3.5 s the row is in the Pinned group, `pinned=true v3`. Two corrections to the lens: the failure is silent, not "This note changed…" — `NoteRow`'s error line comes from its own mutation state, and because the Pinned group and the day groups are different parents (`NotesScreen.tsx:713` vs `:721-726`) the row remounts on every flip, so the rollback lands on a fresh row with no `pin.error`; and the window is not a cellular edge case — it is PATCH RTT plus list-refetch RTT, 400–600 ms on a fast link, 1–3 s on a phone, and "tap Pin, reopen ⋮, tap Unpin" is an ordinary mis-tap correction. Overlap with Decision 6: its backend fix (skip the version check for a pin-only PATCH) removes this path entirely and `queries.ts:271-272` already anticipates it; what this adds is that the app makes its own list stale on every pin, so the 409 needs no second device, and that it fails silently — file this as evidence raising Decision 6's urgency (section 5, owner item 1). Frontend fix regardless: `onSuccess` in `usePinNote` writing `pinned`, `pin_rank`, `version` and `updated_at` from the response through the existing `patchNoteLists` and the detail key; `pin.isPending` in `busy` in both `NoteRow` and `NoteActions`; one Vitest case in `NotesScreen.pins.test.tsx` where the pin PATCH answers 409 and the row leaves the Pinned group (only the reorder rollback is tested today, `:193`; `NoteRow.test.tsx:82` asserts the PATCH body only).

**R4-7 ★ An inbox 401/429 storm has no alarm; the first signal is the budget e-mail about a day in, the throttle is per route so the owner's own devices are refused meanwhile, and the design doc lists neither** — infra, S, DO-NOW. (deploy-ops Medium; security filed the per-route availability trade-off and the missing 401 counter as two Lows; verifier confirmed the structure and corrected the numbers.) The three `AuthorizationType: NONE` inbox routes reach the API Lambda before any check (`handler/inbox.go:62-83 deviceAuthenticated`), so every bad-key POST up to the live throttle (`get-stage`: 5 rps / 20 burst per route, `DetailedMetricsEnabled false`) is paid for. Reproduced: a 4 MiB bad-key POST bills 168–298 ms at 512 MB with the handler reporting `duration_ms 0` — the whole bill is the runtime decoding a 5.6 MB base64 event before the handler runs (the lens's ~0.1 s was an under-estimate); a 1-byte bad-key POST bills 2 ms. At arm64 pricing one saturated route is ≈ $13 gateway + $2.6 Lambda requests + $21–26 duration + $7–10 logs ≈ $45–50/month, ~$1.5/day; ~$140/month with all three saturated (the lens's $30–37 and $90–110 used x86 pricing and the low duration). Nothing alarms on it: the four alarms (`template.yaml:2007-2139`) are Lambda Errors, DLQ depth, ProviderKeyRejected and SpendCapRejections; the comment at `~2035` rules out Throttles and 5xx-rate alarms only, so a 4xx alarm was never weighed; `ApiRequests` carries a Status class only (`metrics.go:104-111`); `devices.go` emits no counter; `counted` skips 401s (`router.go:181-183`), so eleven refused requests left zero events in the Lambda log. The first signal is `MonthlyBudget` (`config/instances/dev.yaml` sets no `monthly_budget_usd`, so the $10 default): the lens missed the FORECASTED > 100 % notification, which at $1.5–4.5/day fires within about a day rather than 2–3, still an e-mail, still a manual remedy. Route-level throttling is shared by all callers, so during a storm the owner's watch gets the gateway's 429 too. `docs/design/inbox.md:114-116`'s threat model lists the per-key 200/day cap, body caps, content-type allowlist and spend cap; nothing on the per-route ceiling or on availability; OpenAPI's inbox 429 is SpendCapped only. Not a duplicate: backlog OF-R records the 5/20 throttle as done — the mitigation this finding says is unmonitored. Bounded worst case needing a deliberate adversary at a URL that is public in the bundle, so not Critical; a public unauthenticated POST surface with no minutes-scale signal is Medium. Fix: one `AWS::CloudWatch::Alarm` on the stage's built-in `AWS/ApiGateway` `4xx` (dimension `ApiId`) Sum ≥ 1000 per 300 s → `AlarmTopic` (inside the ten free alarm-months; 1000/5 min is ~40× anything the app produces); lower the three `RouteSettings` to `ThrottlingRateLimit 1 / ThrottlingBurstLimit 10` (still ~40× the legitimate ceiling of 2,000 requests/day, a 5× cut in the worst case); one bullet in `inbox.md`'s threat model naming the per-route ceiling and the trade-off (a flood at the public URL pauses the inbox; the app itself uses other routes; CloudFront + WAF rate rule is the path if it ever matters). Optional: `obs.Count("InboxKeyRefused", {"Route"})` in `deviceAuthenticated`'s error branch — a counter, no key material — so the 401s are visible from the Lambda side too.
