# Chintan backlog

The running ledger of what has been asked of Chintan and what was decided: the owner's trial notes, the QA pass's findings and the external reviews' items, from 2026-09-04 on, in dated sections. Completed rows stay, so the file is the record of why things are the way they are as much as the queue of what is next. One line per item. Status is one of **fixing** (in a branch now), **next** (agreed, not started), **design** (needs a decision; the proposal is in the note), **answer** (a question, answered in the note), **question** (waiting on the owner), **declined for now** (deliberately not built; the note says why and when to revisit), **dropped** (the owner withdrew it), **done**.

## Features needing design

| # | Item | Status | Proposal |
|---|---|---|---|
| D1 | Advanced cleanup ("smart") vs the current misheard-word cleanup, with raw and cleaned as tabs; re-run over the whole note when new audio arrives | **backend done** (PR: whole-note cleaned view; UI in progress) | Per-recording cleanup stays as it is (`faithful`/`polished` per capture). The note gains one **cleaned view** of the entire body — `structured` (Markdown: short headings, lists for enumerations, filler and repetition removed) or `polished` (prose only, light touch) — generated by the worker's `clean-note` task from the body with the markers stripped, one LLM call through the breaker (`op: clean_note`, input capped at 150 KB, output at 200 KB, refused whole rather than truncated), stored on the note row (`cleaned_body`, promoted like `search_text`). `POST /v1/notes/{id}/clean` (optional `{mode}`) answers 202 and invokes the worker; `PATCH` takes `auto_clean` and `cleaned_mode`; `NoteDetail.cleaned` is `null` or `{body, mode, generated_at, stale, error?}`. Every body write — editor save, append, move, delete — marks an existing view **stale**; with `auto_clean` on, an append (the worker invokes itself), a move or a delete (the API invokes the worker) regenerates it; an editor save never does. The view is **read-only**: edits belong in the body, and the view is regenerated from it. A failed run keeps the previous view and stores a fixed `cleaned.error`. Both exports carry the view (`note.cleaned` in the JSON export, `<slug>-<id>.cleaned.md` from `chintanctl export`). `search_text` stays derived from the raw body. |
| D2 | Move a misfiled recording to another note; splice text by timestamp | **done** | Recording rows get **Move to…** (single) and multi-select on recordings. Moving = remove that capture's marker-delimited paragraph from note A (we have exact markers since yesterday), append it to note B at the position implied by the recording's time relative to B's recordings (chronological insert, not always at the end), re-point the capture row. The transcript is not re-run. Structured mode (D1) re-runs on both notes. |
| D3 | Delete a single recording and its text | **done** | Same primitive as D2's removal step: delete the marker-delimited paragraph, delete the capture row and objects (audio, raw, clean, segments, peaks), typed confirmation. |
| D4 | Download all recordings of a note as one archive; multi-select recordings | **done** | Client-side zip (`fflate`, ~8 KB) from the presigned audio URLs; name files `<note>-<yyyymmdd-hhmm>.webm`; no backend change. Selection UI shared with D2/D3. |
| D5 | AI search / ask the knowledge base | **done** | Frontend landed: **Ask** as a mode of the search field (Search · Ask segment, `mode=ask` in the URL, the question never is), the Ask panel with the answer, "Not in your notes" when ungrounded, source chips that open the note, follow-ups sent with the last six turns as `history`, Save as note, Clear; the thread lives in `sessionStorage`. Backend `POST /v1/ask` + `GET /v1/ask/{id}` (worker retrieval by title/aliases/tags/search_text, top-12 notes packed to a 40k-rune budget, one grounded LLM call, TTL 24 h) is a separate PR to the same contract. No per-note summary attribute after all — ranking over `search_text` covers the current library sizes; embeddings stay "later". Backend 2026-09-05: `POST /v1/ask` (202, idempotent) + `GET /v1/ask/{askId}`; the worker's `ask` task ranks the notes lexically over title/aliases/tags/`search_text`, packs the top bodies within a 40k-rune budget, one grounded LLM call through the breaker (`ops.ask`), sources filtered to what was packed; `ASK#` rows, 24 h TTL. No per-note summary — the bodies are cheap to read for a dozen notes. Embeddings deliberately not built; see `docs/design/ask.md`. |
| D6 | Per-user usage accounting for future admin/billing | **done** | Monthly and daily `USAGE#<user>#…` counters written by the breaker (cost, calls, audio seconds, tokens) plus `GET /v1/usage`. 2026-09-05: per-provider split, `api_requests` per authenticated request, `storage` summary, the tenant's share of the AWS cost, and the `chintanctl usage` admin listing over GSI1. |
