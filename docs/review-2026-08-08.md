# Review — 2026-08-08

Blind, adversarially-verified review of `main` across six independent lenses (security,
correctness, frontend-ux, operability, cost, docs). 56 findings claimed, 49 survived
refutation, 41 distinct after merging duplicates.

## Verdict

**Not releasable.** The stack does not deploy at all: `chintan-dev-staging` is sitting in
`ROLLBACK_COMPLETE` right now, and the capture pipeline has never once deployed
successfully in this account — there is no `chintan-worker-*` Lambda and no capture queue.
Below that, the two headline user journeys are both broken in the shipped frontend: you can
record exactly once per page load, and navigating from Search to Notes replaces the entire
app with an unrecoverable error page.

**Fix first: `infrastructure/template.yaml:341`.** One missing `${Environment}` in the SQS
queue policy's `aws:SourceArn`. It is a one-token change, four of the six lenses found it
independently, and nothing else on this list can be verified end-to-end until it lands.

A caution about sequencing: fixing 341 alone will make `chintan-dev-prod` deploy *and*
silently orphan all its existing content (**H2**). Read H2 before deploying the fix to prod.

## Critical

### C1 — Queue policy names a bucket that does not exist; every deploy fails
`infrastructure/template.yaml:341` (vs `:361`)

Found independently by **operability, docs, security, and cost** — four of six lenses. That
convergence is the strongest signal in this review.

Commit `e816566` renamed the bucket to `chintan-content-${InstanceName}-${Environment}-${AWS::AccountId}`
but left the queue policy's `ArnLike` condition at `chintan-content-${InstanceName}-${AWS::AccountId}`.
The pattern has no wildcard, so it matches nothing that now exists. The adjacent comment
("The name is deterministic, so this is exact, not approximate") asserts exactly what the
code fails to do.

*Failure:* S3 test-publishes when `PutBucketNotificationConfiguration` is applied, is denied,
and `ContentBucket` fails. Verified live, not inferred — stack events for
`chintan-dev-staging/56f62d00-9340-11f1-a009-0a4a1f6a7123` show
`ContentBucket CREATE_FAILED — "Unable to validate the following destination configurations"`
at 2026-08-08T15:48:22Z. README §4 ("Deploy your own") cannot complete on a clean account.
`chintan-dev-prod` will hit the same wall on its next update.

Two lenses added a hedge — "if the validation is lenient, the failure moves to runtime:
uploads succeed, nothing is ever transcribed, no alarm." **That variant is speculative; the
hard create failure is the verified behaviour.** Do not plan around the silent form.

*Cost tail:* every rolled-back attempt strands a `DeletionPolicy: Retain` KMS CMK. us-west-2
now holds three keys described "Chintan dev Cognito refresh-token vault" but only one alias.
Two are unreferenced and bill $1/month forever — on an app whose entire intended idle bill
is one such key.

*Fix:* `!Sub 'arn:aws:s3:::chintan-content-${InstanceName}-${Environment}-${AWS::AccountId}'`.
Then delete the orphans (`aws kms schedule-key-deletion --key-id bc924fec-d634-4a3b-b0f1-efe897e1623d`
and `c539464c-7daa-49ed-a60e-9978ea3c7e7c`). Add a `guardrails-check.sh` assertion that the
SourceArn literal and the BucketName expression are byte-identical, since today they are two
hand-written copies coupled only by a comment.

### C2 — One recording per page load, then the app is wedged
`frontend/src/features/capture/CaptureScreen.tsx:47`

After a successful capture the model is left in terminal `uploaded` and nothing resets it, so
the mount effect's `if (model.state === 'idle') void start(noteId)` guard never fires again.

*Failure:* Walking, one-handed. Record → Stop → Send → "Sent" → auto-return home. Ten seconds
later, tap Record: the app navigates to `/capture`, shows "Sent" and the *previous* recording's
elapsed time for 600 ms, bounces back to Home. The microphone never opens. Reproduced: server
had 1 capture before and 1 after. Only a full page reload restores recording. The failed-upload
path wedges the same way — the only escape is to Discard the previous recording.

*Fix:* `reset()` exists at `store.ts:163` and is referenced nowhere. Call it when leaving a
terminal capture, and change the mount guard to start whenever the model is not busy and not
in `review`/`failed`. Better: arriving at `/capture` with no resumable audio should always mint
a fresh recording, and a resumable one should route to an explicit "you have an unsent
recording" surface.

### C3 — Search and Notes share a query key: hard crash one way, silent data loss the other
`frontend/src/features/search/SearchScreen.tsx:38` and `:44`

SearchScreen's corpus `useQuery` and NotesScreen's `useNotes` `useInfiniteQuery` both key on
`['notes', {state:'active'}]`. Two lenses found this from opposite directions; it is one bug
with two symptoms depending on visit order.

*Failure A (Search first, then Notes):* the plain `Page<NoteWire>` lands in the cache, the
infinite query reads `data.pages` as undefined, and the whole app is replaced by React Router's
raw error page — `Cannot read properties of undefined (reading 'length')` plus a stack trace.
Counted surviving interactive elements: **0 links, 0 buttons**. There is no application error
boundary. On a phone the only escape is OS Back (which returns to Search, and tapping Notes
re-crashes) or knowing to reload.

*Failure B (Notes first, then Search — the common path, since Notes is first on the strip):*
`corpus?.items` is undefined, `rankLocal` gets an empty array, and offline search silently
returns nothing. A/B on identical fixtures: Search-first offline "roof" → 1 result; Notes-first
offline "roof" → **0 results, "Nothing matches 'roof'."** The user is told their note does not
exist. The entire local-search layer is dead on the normal navigation path.

*Fix:* Give the two queries distinct keys (`['notes','corpus',query]`), or have SearchScreen
consume `useNotes({state:'active'})` and flatten `data.pages`. Independently, add a route-level
`errorElement` in `app/router.tsx` so no render error can ever leave zero controls. Add a
regression test that visits `/notes` then `/search` offline and asserts a local hit.

## High

### H1 — The documented first deploy ships the API binary as the worker; SQS then deletes every capture
`scripts/bootstrap.sh:119` / `infrastructure/template.yaml:712`

Found by operability and docs. `bootstrap.sh` calls `build-lambda.sh` with no `--worker-output`,
uploads one object, and passes only `LambdaCodeKey`; `WorkerCodeKey` defaults to `''`, which
template line 712 reads as "share the API zip".

*Failure:* The API entrypoint is `Handler(ctx, events.APIGatewayV2HTTPRequest)`
(`backend/cmd/api/main.go:188`). Feeding a real SQS event to that adapter returns
`{"statusCode":404}` with **`err == nil`**. The event source mapping declares
`FunctionResponseTypes: [ReportBatchItemFailures]` (`template.yaml:802`), and Lambda reads a
success with no `batchItemFailures` key as "whole batch succeeded" — so every uploaded
recording is deleted from the queue on first receive. No retry, no DLQ message, no Errors
datapoint, no alarm. The `GET /v1/health` smoke test still passes, so the deploy reports success.

Three comment blocks actively assert this is safe and are wrong: `build-lambda.sh:6-10`
("there is only one main package (backend/cmd/api)"), `template.yaml:49-52`, and
`ci-deploy-stack.sh:51-54` — all contradicted by `build-lambda.sh:12` ("Two binaries, not one")
four lines below the first, and by `backend/cmd/worker/main.go` existing. The README repeats
the stale claim.

*Fix:* Build and upload both artifacts in `bootstrap.sh` and pass `WorkerCodeKey`, mirroring
`ci-deploy-stack.sh:41`. Delete the three stale comments. Make `WorkerCodeKey` required
(`MinLength: 1`) so the wrong-binary case fails at deploy time rather than at the first
recording.

### H2 — The bucket rename orphans all existing prod content
`infrastructure/template.yaml:361`

`aws cloudformation get-template --stack-name chintan-dev-prod` shows the live bucket is
`chintan-content-dev-338186951935`, which exists and holds prod content. The repo template now
renders `chintan-content-dev-prod-338186951935`. A `BucketName` change requires replacement.

*Failure:* Once C1 is fixed, the next prod deploy creates a new empty bucket, points
`CONTENT_BUCKET` at it, and leaves the populated bucket retained and orphaned. DynamoDB is not
replaced, so every capture row's `audio_key`/`clean_key`/`raw_key` points into a bucket the
Lambda no longer has in its env or its IAM policy (`:576` is scoped to the new ARN). Every
historical note loads with an empty body and every audio playback 404s — with a green deploy
and no alarm.

*Fix:* Do not rename a bucket holding live data. Add a `ContentBucketName` parameter defaulting
to the legacy expression for existing instances, with new instances passing the
environment-qualified one; or ship a documented `aws s3 sync` migration before cutover. Either
way add a pre-deploy guard that refuses to replace a `ContentBucket` containing objects.

### H3 — chintanctl targets the wrong bucket: erasures and backups silently no-op
`backend/cmd/chintanctl/awsports.go:321`, `README.md:187`

Found by security, operability, and docs. The CLI builds
`fmt.Sprintf("chintan-content-%s-%s", g.instance, account)` — no environment — while the table
name at `:310` correctly includes it. README:187 documents the same wrong convention.

*Failure (erasure):* `chintanctl erase --tenant <sub> --apply` deletes the DynamoDB index rows
and the credential mirror, reports `objects deleted: 0`, and exits 0 — while every recording,
transcript and note markdown remains in the live bucket, now unreferenced by any index and
therefore invisible to any later erase or export. This is a deletion request that reports
completion and deletes none of the recordings.

*Failure (backup):* `chintanctl backup` writes `backup.json`, whose presence README:181 says
"means the backup finished", containing zero S3 artifacts. This is the tool README:172
introduces as the fix for "nothing backed up S3 content at all". Cross-environment is worse:
`--environment staging` reads index rows from staging and blobs from *prod's* bucket.

Whether the wrong name resolves to an orphaned bucket or to `NoSuchBucket` depends on whether
the account predates `e816566` — pre-rename accounts fail silently, fresh accounts fail loudly.

*Fix:* Resolve the bucket from the stack output `ContentBucketName` (`template.yaml:1287`)
rather than re-deriving the convention in a third place; keep `--bucket` as an override. Update
the stale comment at `awsports.go:286` and README:187. Make erase/export fail loudly when the
object count is zero but index rows reference S3 keys.

### H4 — The presigned upload URL is unbounded and replayable for 30 minutes
`backend/internal/upload/upload.go:70`

`max_bytes` is returned to the client as advice only. `X-Amz-SignedHeaders` is exactly
`host;x-amz-tagging` — neither Content-Length nor Content-Type is signed. `MaxCaptureBytes`
is checked only against the client's self-declared `size_bytes` at `service/capture.go:160`,
never against the bytes actually written. This contradicts `service/capture.go:30-34`, which
claims this is what stops "the URL open to an unbounded upload".

*Failure:* Request a URL for a 1 KB clip, PUT 5 GB. S3 accepts it. The bucket has versioning
enabled and the URL lives 1800 s, so the same URL writes further 5 GB versions. Unbounded
storage charges, the worker streaming a multi-GB object to Groq, and — since
`ExpireCaptureAudio` only exists under `HasRetention` — no expiry unless `RetentionDays` is
set. Same for anyone who obtains a leaked URL (browser history, HAR, proxy log) inside 30 min.

*Fix:* Presigned PUTs cannot carry a length constraint. Either switch to a presigned POST with
a `Content-Length-Range` policy condition, or enforce after the fact — the worker already
receives `r.S3.Object.Size` (`pipeline/worker.go:140`); reject, delete and fail any capture
over `MaxCaptureBytes` before transcription. Sign Content-Type so the declared container is
binding. Drop `max_bytes` from the response or document it as advisory.

### H5 — Cancelling during microphone acquisition leaves the mic live forever
`frontend/src/features/capture/recorder.ts:138`

`start()` sets `this.stopping = false` *after* awaiting `requestMicrophone()`, so a cancel
during acquisition is erased when the promise resolves and the recorder starts anyway.

*Failure:* First use, permission prompt, cold radio, or Bluetooth handover makes acquisition
slow. The screen says "Starting the microphone…" with a Cancel button; the user taps it and
returns Home. Instrumented with a 3 s `getUserMedia` delay: 7 seconds after Cancel the track
was still `readyState=live, enabled` and IndexedDB held 7,846 bytes of still-growing chunks.
The OS recording indicator stays on, the battery drains, and the audio is orphaned forever —
`discardCapture` already ran, and with no `captures` row `unconfirmedCaptures()` will never
list or prune it.

*Fix:* Make `start()` abort-aware. Move `this.stopping = false` to the top of `start()`, before
the await; immediately after the await resolves, check for a cancel and if so stop every track
on the returned stream, skip the recorder and the wake lock, and return.

### H6 — Opening the PWA offline at any unvisited URL shows the word "Offline"
`frontend/src/sw.ts:98`

Workbox precaches the shell as `/index.html?__WB_REVISION__=<hash>`, but the fallback is
`caches.match('/index.html')` with no `ignoreSearch`, so it misses and the worker returns the
bare 503 `new Response('Offline')`.

*Failure:* Car park, lift, tunnel, dead cell. A blank white page containing one word, no app,
no controls, no way back. Reproduced at `/settings` and `/capture`. This includes the manifest's
own `Record a thought` shortcut (`url: 'capture'`) — the product's headline hands-free
affordance: long-press icon → "Record a thought" → "Offline". Previously-visited URLs work off
the runtime cache, which is exactly why casual testing misses it.

*Fix:* `(await cache.match(request)) ?? (await caches.match(SHELL_URL, { ignoreSearch: true }))`,
or use Workbox's `createHandlerBoundToURL`/`matchPrecache`. Also derive `SHELL_URL` from the
build base — on a Pages sub-path deploy (`VITE_BASE=/repo/dev/`) the hard-coded constant is
wrong for a second reason.

### H7 — System Back inside the autosave debounce silently discards note edits
`frontend/src/features/notes/useNoteEditor.ts:143`

The unmount cleanup clears the pending 1.2 s timer without flushing it, and `beforeunload` does
not fire on client-side navigation.

*Failure:* Type "Ellis quoted nine hundred pounds." and use the system Back gesture — the
primary one-handed way to leave a screen — within 1.2 s of the last keystroke. Zero PATCHes,
stored body unchanged, no warning: the indicator said "Unsaved changes" and then the screen was
gone. The in-app back arrow only works by accident, because tapping it blurs the textarea and
`onBlur` calls `saveNow()`; removing an element from the DOM fires no blur.

*Fix:* Flush rather than drop — `if (timer.current) { clearTimeout(timer.current); void save(); }`
using the `latest` mirror ref (the fetch survives unmount). Belt and braces: `useBlocker` while
`hasUnsavedWork(model)`, and flush on `visibilitychange` → hidden to cover app-switching.

## Medium

**M1 — WebAuthn challenges never expire in production.** `backend/internal/repository/dynamo.go:1112`.
`GetWebAuthnChallenge` ignores `ExpiresAt`, `service/webauthn.go:342` does not check it, and the
library's own `Timeouts.*.Enforce` is left off — so the only bound is DynamoDB's best-effort TTL
sweep, which AWS documents as up to 48 h and which explicitly still returns expired items to
reads. An abandoned ceremony's `challenge_id` replays days later into a live Cognito token set;
registration re-binds the KMS-sealed refresh vault the same way. *Fix:* check
`time.Now().Unix() > entry.ExpiresAt` in `loadChallenge` (as `memory/memory.go:511` already
does), and set `Timeouts.Login.Enforce`/`Registration.Enforce = true` at `service/webauthn.go:76`.

**M2 — Deploy role has full control of every KMS key in the account.** `infrastructure/bootstrap.yaml:213`.
`kms:PutKeyPolicy`, `ScheduleKeyDeletion`, `DisableKeyRotation`, `DeleteAlias` on `Resource: '*'`.
Anyone who can trigger a deploy (push to the deploy branch, compromised runner or OIDC subject)
can rewrite another project's CMK policy to allow itself `kms:Decrypt` — a same-account key
policy naming the principal is sufficient authorization — or schedule that key for deletion.
The boundary does not stop it: `boundary.json:5` allows `kms:*`, the name-prefix deny lists no
KMS ARNs, the tag deny lists no `kms:*` action, and `DenyDecryptingProviderSecrets` only fires
for `/chintan/*` SSM encryption contexts. The template header's "passbook-* is out of reach"
does not hold for KMS, because CMK ARNs are UUIDs, not name-prefixed. *Fix:* keep only
`CreateKey`/`ListAliases`/`DescribeKey` on `'*'`; condition every mutating action on
`aws:ResourceTag/Project: chintan`, and add those actions to the boundary's tag-deny list.

**M3 — Deploy role can modify any Cognito user pool in the account.** `infrastructure/bootstrap.yaml:161`.
`DeleteUserPool`, `UpdateUserPool`, `SetUserPoolMfaConfig`, `Delete/UpdateUserPoolClient` on
`'*'`. The comment's justification ("pool IDs are service-generated, so there is no ARN to match
before the pool exists") is true only for `CreateUserPool`. A compromised or buggy deploy can
add a permissive callback URL or enable implicit grant on another app's client, or turn its MFA
off. The boundary's `Null aws:ResourceTag/Project = "false"` means the deny only applies to
resources that *already* carry a Project tag, so an untagged foreign pool falls through, and
`DeleteUserPool` is permitted when `aws:CalledVia` is CloudFormation — which is how a deploy
runs. *Fix:* `CreateUserPool` alone on `'*'`; everything else conditioned on the Project tag.
Deny absent-tag resources for `cognito-idp:Delete*/Set*/Update*`.

**M4 — Per-IP rate limit is bypassable by header rotation.** `backend/internal/handler/ratelimit.go:118`.
`clientIP` prefers the left-most `X-Forwarded-For` entry — caller-supplied — over `r.RemoteAddr`,
which the Lambda adapter writes from `requestContext.http.sourceIp`. API Gateway *appends* to the
client's header rather than replacing it, so a rotating XFF gives every request a fresh
`ipWindow` and the 10/min limit never fires on the two unauthenticated WebAuthn routes. Each
request reaches a DynamoDB Query and GetItem — the exact unauthenticated database-cost lever the
comment at `:14-18` says the limiter exists to close — and 4096 attacker-chosen keys force the
`evictExpiredLocked` reset that forgives a whole window. *Fix:* key on
`net.SplitHostPort(r.RemoteAddr)` first; if XFF must be used, take the right-most entry and cap
the parse count.

**M5 — `verbatim` and `created_at` are destroyed on every note read.** `backend/internal/repository/dynamo.go:277`.
`noteFromItem` rebuilds `NoteIndex` from promoted attributes only, and `noteItemAttrs`
(`:241-264`) never writes either field as a top-level attribute — so neither survives a
round-trip, and the next `UpdateNote` re-serialises `false` into the blob permanently.
OpenAPI (`docs/api/openapi.yaml:759`) states verbatim is "returned on every read, because the
toggle has to render the state it is in"; against DynamoDB it can never be true, so dictation
the user marked as must-not-be-reworded goes through cleanup anyway. Verified against the repo's
own `fakeDynamo`: stored `verbatim=true created_at=2026-08-08T15:57:21Z` → read `false`, `""`.
`dynamo_test.go` only asserts ID/Title/Version, so no test can catch a dropped field. *Fix:*
add both to `noteItemAttrs`, `noteListProjection` (`:135`) and `noteFromItem`, or overlay
attributes onto the unmarshalled blob as `captureFromItem` already does (`:530-563`). Add a
round-trip test over every exported field.

**M6 — Append claim lease is shorter than the SQS visibility timeout, so text lands twice.**
`backend/internal/pipeline/pipeline.go:594`. `AppendClaimLease` is 900 s
(`repository/store.go:82`) but `CaptureQueue.VisibilityTimeout` is 960 s (`template.yaml:307`).
A worker that writes the note body and dies before `CompleteCaptureAppend` (Lambda 900 s
timeout, 5 failed version conflicts in `refreshNoteIndex`, or a transient DynamoDB fault) is
redelivered at T+960 with an already-stale claim, re-claims, and appends the identical
paragraph. `maxReceiveCount: 3` means up to three copies. This is precisely the duplicate-append
defect the package doc claims to have closed; the existing tests only exercise an immediate
retry where the claim is still fresh. *Fix:* make the lease strictly longer than the visibility
timeout (or derive it from it), and make the append idempotent independent of the claim. Add a
test seeding `AppendClaimedAt = now-960s`.

**M7 — A losing editor save destroys a concurrent voice append before it loses.**
`backend/internal/service/notes.go:283`. The body is written to S3 with an unconditional Put
*before* the version-checked index write. If the pipeline's append lands between the check at
`:255` and the Put, the editor's `objects.Put` wipes the spoken paragraph from S3 forever and
*then* fails with `ErrVersionConflict` — the user is told "conflict, re-read" about text that no
longer exists, and the index (version 5, snippet from the merged body) disagrees with the
object. The comment at `:253-254` asserts the opposite ("a losing writer does not leave a
rewritten body behind"); the pre-check narrows the window but cannot close it, because S3 is
never written conditionally on this path. *Fix:* use `objects.PutIfMatch` with the ETag read at
the start (as `pipeline.appendToNote` already does) and map `ErrPreconditionFailed` to the same
409. Add a test interleaving an append between the check and the Put.

**M8 — Search silently drops matches it will never return.** `backend/internal/service/search.go:121`.
Hits are truncated to `limit` but the returned cursor is the store cursor from past every note
scanned. 120 notes matching "roof" with `limit=50`: all 120 are collected from one store page,
50 are returned, the cursor is empty because the store is exhausted, and **70 matching notes are
unreachable**. Verified: paging to exhaustion returned 50 distinct notes out of 120. *Fix:* stop
reading store pages once `want` hits are collected and issue a cursor that resumes inside the
partially consumed page, or carry the surplus in the cursor. At minimum, never discard hits no
later request can return.

**M9 — `excerpt()` can panic on user-controlled text, 5xx-ing search for that tenant.**
`backend/internal/service/search.go:217`. The byte offset is computed in
`strings.ToLower(text)` and then used to slice the *original* `text`. For runes whose lowercase
form is longer in UTF-8 — U+023A `Ⱥ` (2 bytes) → U+2C65 `ⱥ` (3 bytes) — the offset exceeds
`len(text)`. Snippet `"ȺȺȺx"` (7 bytes, 10 lowered) searching "x": `strings.Index` returns 9,
`text[:9]` panics. There is no `recover()` anywhere in the backend, so `GET /v1/search` 5xxs on
every such query. Snippets come from dictated or typed note text, so the input is fully
user-controlled; below the panic threshold the excerpt window is merely off by whole runes.
*Fix:* locate the term by rune index on `[]rune(strings.ToLower(text))`. Table/fuzz test with
`Ⱥ`, `İ`, KELVIN SIGN.

**M10 — A tenant's spend cap never reaches the thing that enforces it.** `backend/cmd/worker/main.go:94`.
The breaker is built from the instance-wide `DAILY_SPEND_CAP_MICROS` only, which defaults to 0 —
"record but never enforce". A tenant setting `daily_spend_cap_micros = $1` is honoured solely by
`service.SpendGate` (`service/spend.go:69`), a courtesy check done once at `POST /v1/captures`.
So a capture accepted at $0.99 spent can run a 20-minute transcription plus two LLM calls
unbounded, and anything already queued is unbounded outright. The breaker package doc claims
"there is no path to a provider that skips the spend check" — the path is not skipped, it is
checked against the wrong number. *Fix:* resolve the tenant cap inside `Breaker.Do`. Test that a
tenant-set cap actually refuses a provider call in the pipeline.

**M11 — Offline notes list tells the user their library is empty.** `frontend/src/screens/NotesScreen.tsx:38`.
TanStack Query *pauses* offline queries rather than failing them, so neither `isLoading` nor
`isError` is true and the brand-new-user empty state renders: "Nothing here yet. Tap the record
button and say something." — directly under a banner reading "Offline — showing saved notes."
For a user with a full library walking into a tunnel, their entire library appears deleted. The
correct copy already exists at `:34` but is gated on `isError`, which never becomes true here.
*Fix:* branch on connectivity and fetch status — `!online && notes.length === 0` → offline copy;
keep the empty state for `online && !isLoading && !isError && notes.length === 0`. Consider
surfacing `fetchStatus === 'paused'` distinctly.

**M12 — `needs_target` asks a question the UI provides no way to answer.** `frontend/src/features/capture/ProgressCard.tsx:113`.

**M13 — Backing out of capture leaves the mic recording with no indicator anywhere.**

**M15 — The transcript "Cleaned" tab is permanently empty.** `frontend/src/features/notes/NoteDetailScreen.tsx:287`.

**M16 — The orphan report is blind to exactly the two resources that survive teardown.** `scripts/teardown.sh:167`.
It scans S3, DynamoDB and SSM only. KMS keys and Cognito user pools — the two carrying
`DeletionPolicy: Retain` — are not scanned, and they cannot be found any other way:
`cleanup-aws.sh` handles KMS but only by enumerating a *live* stack's resources (`:97`), so it
cannot see a key left by a stack that rolled back and was deleted. After the C1 rollback loop,
`teardown.sh --apply` reports "no orphaned resources" while two CMKs bill $1/month each, and
`cleanup-aws.sh --environment staging` cannot help because the stack no longer exists. Every
future failed deploy adds another $1/month on the same blind spot. *Fix:* scan
`kms list-aliases`/`list-keys` filtered on the `Project=chintan` tag and
`cognito-idp list-user-pools` on the name prefix, printing the `schedule-key-deletion` command.
Cheaper root-cause fix: drop `DeletionPolicy: Retain` from `TokenVaultKey` and rely on KMS's own
7–30 day pending-deletion window, which already provides the recovery the Retain is buying.

## Low

**L1 — Note IDs are the raw wall clock.** `backend/internal/service/notes.go:151`:
`fmt.Sprintf("note_%d", time.Now().UnixNano())`, no random component. Guessable to clock
resolution, so any future path treating a note ID as a capability (share link, unauthenticated
preview, a widened bucket policy over `tenants/<user>/notes/<id>/note.md`) is brute-forceable.
Same-nanosecond collisions surface as an unexplained 409 on note creation. Capture IDs
(`capture.go:189`) and export IDs (`export.go:113`) already use `crypto/rand`; notes are the
outlier. *Fix:* keep the sortable time prefix, append 8 random bytes.

**L2 — A transient DynamoDB fault silently sends dictation to a brand-new note.** `backend/internal/pipeline/pipeline.go:417`.
`route()` tests `err == nil && service.NoteIsActive(note)`, so a throttle or 5xx on `GetNote`
falls through to creating a second note with the same subject. The error is never logged and
never retried; `ErrNotFound` and transient faults are treated identically. *Fix:* fall through
only on `ErrNotFound`/archived; return other errors so SQS redelivers.

**L3 — A filtered capture list can return an empty first page with a cursor.** `backend/internal/service/capture_list.go:87`.
The status filter is applied after the store paginates, and the store query has no
`FilterExpression`. One `needs_target` capture behind 60 newer ones means
`GET /v1/captures?status=needs_target` returns `items: []` with a non-empty cursor, so a
"needs your attention" list that fetches page one shows nothing while the capture sits
indefinitely. *Fix:* keep pulling pages until `limit` kept items or exhaustion (bounded, as
`dynamo.go:316` already does), or push the filter into the query.

**L4 — `Settings.RetentionDays` is validated, stored, returned, rendered, and read by nothing.**
`backend/internal/service/settings_validate.go:46`. Expiry is driven entirely by the
`ExpireCaptureAudio` lifecycle rule (`template.yaml:429-437`) filtering a fixed tag with the
deploy-time `RetentionDays` parameter. The UI shows 30 days; audio lives as long as the stack
says. `cmd/api/main.go:89` explicitly claims this exact state was fixed. *Fix:* drop the
per-tenant field and document retention as deploy-time, or make it real via per-tenant retention
tags and matching rules.

**L5 — A failed server search reports "Nothing matches" with no hint it failed.** `frontend/src/features/search/SearchScreen.tsx:61`.
`usingCachedOnly` requires `merged.length > 0`, so a captive portal or dead API while
`navigator.onLine` is true — the exact case the codebase's own `useOnline` comment calls out —
shows 0 results and no `.search-offline` notice. The user is authoritatively told the note does
not exist when the search never ran. *Fix:* `const serverUnavailable = !online || server.isError;`
and always render the notice — a zero-result search is when the user most needs to know.

**L6 — The offline banner claims cached notes that do not exist.** `frontend/src/offline/OfflineBanner.tsx:17`.
There is no query persister, so on an offline cold start the banner reads "Offline — showing
saved notes." directly above "You are offline and no notes are cached on this device yet."
Its own doc comment criticises v1 for "stale data presented as live data"; this presents absent
data as saved data. *Fix:* make the banner state-driven, or add `query-persist-client` over the
IndexedDB plumbing already present in `offline/db.ts`.

**L7 — A stack in `ROLLBACK_COMPLETE` makes every later deploy fail opaquely.** `scripts/deploy.sh:116`.
`stack_exists` (`lib/common.sh:408`) is just `describe-stacks` succeeding, which is true for
`ROLLBACK_COMPLETE`, so `CHANGE_SET_TYPE=UPDATE` and CloudFormation refuses (such a stack can
only be deleted). `set -e` aborts on a raw ValidationError with no recovery instructions. This
is the live state of `chintan-dev-staging`, and the six `DELETE_COMPLETE` staging stack IDs show
the real operator workflow has been "delete by hand and retry" six times today.
`cleanup_change_set` anticipates the `REVIEW_IN_PROGRESS` wedge but not this one. *Fix:* branch
on stack *status*: delete-and-CREATE for `ROLLBACK_COMPLETE`/`REVIEW_IN_PROGRESS`, explicit
`continue-update-rollback` message for `UPDATE_ROLLBACK_FAILED`. Same for `bootstrap.sh`.

**L8 — The stack-status filter hides failures and can delete a live stack's secrets.** `scripts/lib/common.sh:439`.
`list_chintan_stacks` excludes `DELETE_FAILED`, `CREATE_FAILED` and all `*_IN_PROGRESS`.
(a) A half-failed teardown leaves `DELETE_FAILED`; the retry prints "nothing to tear down" and
exits 0 while a partially deleted stack with Cognito deletion protection now *off* sits in the
account, invisible to the orphan report. (b) `cleanup-aws.sh:120` computes `SIBLINGS` from the
same function, so if `chintan-dev-prod` is `UPDATE_IN_PROGRESS` during a concurrent CI deploy,
`SIBLINGS` is empty and lines 239-245 delete `/chintan/dev/groq_api_key` and `llm_api_key` —
prod's provider keys — breaking every prod transcription. `cleanup-aws.sh:12-17` names this
exact class of bug as the v1 defect it fixes. *Fix:* invert the filter to exclude only
`DELETE_COMPLETE`; report failed/in-progress stacks explicitly; make the SIBLINGS guard fail
closed.

**L9 — The spend breaker cannot be enabled through the supported deploy path.** `scripts/list-instances.sh:129`.
`DailySpendCapMicros` is absent from the `optional` dict, which is the only channel from
instance config to CloudFormation parameters, and `ci-deploy-stack.sh:59-64` forwards only what
that dict produces. So every CI-deployed stack gets `DAILY_SPEND_CAP_MICROS=0`, and
`HasSpendCap` (`:111`) is false so `chintan-<i>-<env>-spend-cap-tripped` is never created. A
runaway provider loop is bounded by nothing but the AWS Budgets email. The README config table
omits it too, so the gap is undiscoverable from the docs. *Fix:* add the key to the dict,
document it with its microdollar unit, and set a non-zero default in the shipped configs.

**L10 — Noncurrent object versions are never expired under default settings.** `infrastructure/template.yaml:436`.
Versioning is enabled unconditionally (`:455`) but `NoncurrentVersionExpiration` is nested
inside the `HasRetention` `!If`, and `RetentionDays` defaults to 0 with neither shipped config
overriding it. Deleting a capture or overwriting a pipeline artifact frees nothing, ever;
`ExpireDeleteMarkers` cannot compensate because a delete marker only expires once no noncurrent
versions remain behind it. `aws s3 ls` shows an empty-looking bucket while every `audio.webm`,
`raw.json`, `clean.json`, `segments.json` and `peaks.json` is still billed. *Fix:* move
`NoncurrentVersionExpiration` out of the conditional (`NoncurrentDays: 7`). Recovery is
additionally blocked by **H3**.

**L11 — `AdvancedSecurityMode: ENFORCED` moves the pool off the free tier.** `infrastructure/template.yaml:132`.
It puts the user pool on the Cognito Plus plan, billed from the first MAU, where Essentials
includes 10,000 free. The live pool `us-west-2_mhEsaNtml` is presently `ESSENTIALS` with 2 users,
so the next deploy flips it. The amount is trivial (~$0.04/month/instance) but it converts a $0
line into a permanent per-user charge on an app whose whole point is one user, in exchange for
adaptive auth on a pool that already has optional TOTP and a 12-char password policy. *Fix:*
`AUDIT` (or omit `UserPoolAddOns`) unless adaptive auth is genuinely wanted — and if it is, say
so in the comment, which currently describes the feature and not the tier change it causes.

**L12 — `GET /v1/health/ready` is documented and coded as public but answers 401.** `docs/api/openapi.yaml:67`.
`security: []` at `:73`, `public()` at `handler/routes.go:19`, but the template declares
`AuthorizationType: NONE` only for `GET /v1/health` (`:908`), the OPTIONS preflight and the two
WebAuthn login routes; everything else falls through `$default` with the JWT authorizer. So the
deployed endpoint returns API Gateway's `401 {"message":"Unauthorized"}` — never reaching Lambda
and not `application/problem+json`, breaking the document's own rule 2. An uptime probe
configured from the spec alarms permanently, and the frontend's `api.ready()`
(`endpoints.ts:52`, `anonymous: true`) can never succeed. The document also contradicts itself:
`:12` says every route except `/v1/health` and the two WebAuthn routes needs a token.
`openapi_conformance_test.go` exercises the Go router directly and never the gateway route
table. *Fix:* pick one of the three and make all three agree; add a guardrail that the
template's NONE routes match the operations declaring `security: []`.

**L13 — The CI table omits three of twelve gating jobs.** `README.md:207`. Missing `vite-env`,
`contract` (fails on stale committed fixtures) and `e2e` (Playwright); the `frontend` row omits
`bun run lint`, which is eslint *plus* `scripts/check-tokens.mjs` — the rule forbidding literal
colours and font sizes outside design tokens. A contributor who adds `color: #1B4332`, runs the
four documented commands (all green) and opens a PR is blocked by three gates the README never
mentions and gives no local command for. `README:195` also says the workflow runs on every PR;
it also runs on pushes to `main` and `feat/v2`. *Fix:* add the rows and the local commands
(`CHINTAN_UPDATE_FIXTURES=1 go test ./internal/handler/ -run Contract`, `bun run e2e` with
`bunx playwright install chromium`).

**L14 — The "real schema" omits a block both shipped configs contain.** `README.md:75`.
`config/instances/dev.yaml:3-9` and `dev-staging.yaml` carry a `pwa:` mapping (name, short_name,
description, theme_color, background_color). The README table says "This is the real schema" and
does not list it; `list-instances.sh:106-146` reads five known keys and drops unknowns without
warning; nothing else reads them — `frontend/vite.config.ts` hardcodes `short_name: 'Chintan'`
and `theme_color: '#FBF9F4'`. A forker sets `pwa.name: MyNotes`, deploys, installs the PWA, and
it is still called "Chintan". This also falsifies `list-instances.sh:5-13` ("a field removed
from a config breaks the deploy rather than being silently ignored"). *Fix:* wire the block
through to `VITE_*` and document it, or delete it from both configs — and add unknown-key
rejection so a typo fails at `instance-configs` in CI rather than on a user's home screen.

**L15 — "Every script has `--help`" is false.** `README.md:18` vs `scripts/ci-deploy-stack.sh`,
which parses no flags at all: `--help` prints `error: INSTANCE is required` and exits 1

**L16 — An entire route is undocumented and the conformance test cannot see it.** `backend/internal/handler/routes.go:34`.
`POST /v1/notes/{noteId}/archive` returns 200 with a Note body (`notes.go:207-221`) while its

## What this review did not cover

Nothing below was examined; absence of a finding here is not evidence of correctness.

- **Any end-to-end run of the capture pipeline.** It has never deployed successfully in this
  account, so transcription quality, router accuracy, cleanup behaviour, provider error handling
  and real latency are entirely unverified. Several backend findings are reasoned from code and
  fakes, not from observed production behaviour.
- **Load, concurrency and soak.** No sustained-traffic testing, no DynamoDB throttling behaviour
  under real volume, no Lambda cold-start or concurrency-limit analysis. The append-duplication
  and optimistic-concurrency findings are race analyses, not reproduced races.
- **Dependency and supply chain.** No audit of Go modules or npm/bun packages for known CVEs,
  transitive risk, or lockfile integrity beyond whatever `backend-vuln` already runs in CI.
- **Authentication end-to-end.** No live WebAuthn ceremony against real authenticators, no
  Cognito token lifetime/refresh/revocation testing, no session-fixation or CSRF review of the
  browser flows.
- **Accessibility and device matrix.** No screen-reader pass, no contrast audit, no keyboard-only
  navigation, no testing on real iOS Safari or older Android WebViews. The frontend findings come
  from a single browser environment.
- **Data migration and restore.** `chintanctl restore` was never exercised against a real backup,
  and no backup/restore round trip was performed. **H3** means existing backups may be empty; that
  was inferred, not confirmed against a real archive.
- **The full IAM boundary.** Two wildcard grants were examined in depth (**M2**, **M3**). The rest
  of `bootstrap.yaml` and `agent-policies/boundary.json` was not systematically enumerated, and
  no policy simulator run was performed.
- **Test quality.** Several findings note that existing tests pass while production is broken.
  The suite was not otherwise assessed for coverage, flakiness, or assertion strength.
- **Uncommitted work in `frontend/`.** Another agent was editing `AppShell.tsx`, `NoteRow.tsx`,
  `shell.css` and `tokens.css` during this review; findings reference committed `main` and may be
  stale for those four files.
